# Seroevents: project overview and production roadmap

Reviewed 15 September 2026, repository commit `c0286e5`. This is a source-code and build assessment. Business statements are descriptions of the site's content, not independently verified claims. No application features were changed during this review.

## What the product is today

Seroevents is a public company and conference website for scientific events and healthcare engagement in the UAE. Its purpose is to establish credibility, explain services, promote forthcoming conferences, document past events, and attract attendees, scientific contributors and commercial/institutional partners.

Its audience includes healthcare professionals, hospital leaders, academics, scientific committees, medical societies, pharmaceutical companies and other healthcare organisations. Services advertised include scientific programme development, conferences, education, speaker coordination, partnerships and event operations. These are business services described on the website; the software does not automate those operations.

Today it is an informational website with email-based enquiries. It has no attendee accounts, admin dashboard, database, payment processing, registration records, ticketing, check-in or certificate generation.

## Important feature boundaries

### Social sharing

Treat sharing as a first-class post-registration action and an event-discovery feature. Store event-specific caption templates, hashtags and the verified official LinkedIn page URL in the CMS. The exact LinkedIn account/page mentioned in the meeting must be confirmed; do not invent its handle.

The baseline should provide a downloadable card, editable/copyable caption and a sharing entry point. Direct posting, automatic image attachment, prefilled captions and actual tagged mentions require platform capability verification before being promised. Plain text containing an @name must not be treated as proof of a resolved platform mention. Publishing should remain an explicit attendee action. Record a share-button click as an intent, not as a confirmed published post.

Keep the public announcement image separate from the private invitation: never include the admission QR or private serial in an image intended for public social media.

### Registration and invitation

Create one registration per attendee/event with an explicit status. Decide whether registration immediately confirms admission or requires approval. Generate passes only for eligible registrations, make repeated requests safe, and define what happens to passes when a registration is cancelled or event details change.

The QR should identify an opaque, unguessable pass token rather than expose attendee details or use the visible serial as a credential. If used for check-in, validate event, pass state and prior use on the server (prior use is shown to staff but does not block valid re-entry), and record the check-in outcome. A generated QR image by itself does not implement admission control.

### Activity log: a core requirement

Use a structured activity stream from the beginning, with at least event ID, UTC timestamp, actor ID where known, action, affected entity, result and request/correlation ID. Suggested actions include sign-in success/failure, explicit sign-out, session expiry/revocation, event-page view, registration/cancellation, document delivery, pass issue/check-in and admin create/update/delete.

Distinguish explicit logout from session expiry: closing a browser does not provide reliable proof of logout. Similarly, an authorised document response records delivery, not proof that the person saved or read it. Event-page viewing is different from physical event attendance. Anonymous views cannot reliably identify a person; authenticated views can be associated with an account, but view telemetry remains best-effort.

Write security and business actions from trusted server code. Capture page views as telemetry with deduplication rules; do not give them the evidential weight of successful registrations or admin mutations. Store document versions so history identifies which agenda was delivered. Serve restricted files through authorised download endpoints or controlled links instead of permanent public URLs.

Logs must be append-only to normal application roles, protected from ordinary CMS edits/deletion, and visible only to authorised admins. Do not log passwords, session secrets, raw QR tokens or document contents. Define retention, user-facing disclosure and any deletion/anonymisation process deliberately; “all activity” should not mean unlimited collection of sensitive data. Any security-critical action that cannot be durably logged needs a defined failure/retry policy.

## Proposed data and access model

| Entity | Purpose / relationships |
|---|---|
| Users / role assignments | Attendee identity and explicitly controlled admin access |
| Sessions / authentication events | Session lifecycle or provider references; authentication audit trail |
| Events | Dates, timezone, venue, description, publication and registration state |
| Event media | Ordered images and gallery assets linked to events |
| Speakers / event speakers / sessions | Reusable faculty and programme content where needed |
| Documents / document versions | Resources, access rules and event association |
| Registrations | User-to-event relationship, status and timestamps; unique user/event constraint |
| Passes / check-ins | Private invitation serial, token hash, validity and admission records |
| Announcement templates / generated assets | Branded public cards and caption template versions |
| Enquiries | Contact requests and handling status |
| Activity events | Actor/action/resource/outcome/time, supporting admin audit and attendee history views |

This is a conceptual schema, not a final migration. Attendee history should draw registration state from registrations and download activity from delivery records; logs do not replace the business tables. Archive or soft-delete content referenced by registrations rather than destroying historical relationships. Attendees must never be able to assign themselves admin access or read another attendee’s records. Admin actions and role changes must themselves be audited.

## Architecture implications

Next.js and TypeScript remain viable foundations, but the current static deployment alone cannot supply authenticated server operations, private downloads, persistent registrations or audit logging. Introduce a backend, relational database, authentication/session management, private file storage, transactional email and image/pass generation. Public pages may still be statically rendered where useful. Hosting and service vendors remain undecided.

The existing content can seed the new event model. Reuse useful components and SEO work, while redesigning the user journeys and replacing duplicated hardcoded data. Design permissions and logging alongside the database, before adding user-facing mutations.

## Updated development sequence

1. **Define the product and redesign journeys.** Confirm registration approval, authentication, document access, sharing and admission behaviour; produce the sitemap, wireframes and visual system for public, attendee and admin areas.
2. **Build the platform foundation.** Stabilise dependencies/build checks; define database relationships, server permissions, authentication, storage and durable audit events. Establish development/staging/production separation and migrations.
3. **Build CMS and event discovery.** Admin event/media/document CRUD, publication workflow, redesigned upcoming/past galleries, event pages and migration of current content.
4. **Build attendee flows.** Registration, reliable enquiries, email confirmations, controlled downloads, account history and private passes. Validate authorisation and logging for every operation.
5. **Build social sharing and admission.** Branded announcement cards, captions/hashtags, verified platform sharing behaviour and QR validation/check-in once its workflow is confirmed.
6. **Validate and launch.** Exercise complete user/admin journeys, permission boundaries, duplicate registrations, allowed pass re-entry, revoked-pass rejection, email failures and audit completeness; review responsive/accessibility behaviour, backups and recovery, content and production operations.

## Acceptance checkpoints

- An attendee can register and see the correct event in their own history; another attendee cannot access that record.
- A permitted document download appears with document version and timestamp; unauthorised access is rejected.
- Every successful sign-in and explicit sign-out has a corresponding actor/time/outcome record; expiry is identified separately.
- An event-page visit is labelled as a page view, not attendance.
- Only admins can use CMS read/write endpoints; hiding navigation alone is insufficient.
- Admin changes create protected audit entries.
- Confirmed registration produces a private invitation and a separate public announcement card.
- The public card contains no admission credential. Any admission scanner rejects invalid or revoked passes while permitting and recording re-entry with valid passes.
- Share copy includes approved event details and tags; platform mentions and actual posting behaviour are verified before acceptance.
